# 航海日志出击状态官方 API 化设计

## 目标

航海日志「出击」记录的「状态」继续表示节点类型，并严格使用游戏 API 返回的节点事件信息。删除把旧数字或未知值显示为「进击」的错误兜底，避免将节点类型与玩家的进退选择混为一谈。

## 已确认行为

- 「状态」列继续显示节点类型，例如「普通战斗」「Boss 战」「空袭战」「路线选择」。
- 不把「状态」列改成玩家操作记录，不新增「进击／撤退」字段。
- 新日志继续读取 `/kcsapi/api_req_map/start` 与 `/kcsapi/api_req_map/next` 响应中的 `api_event_id`、`api_event_kind`。
- `BattleContext.nodeTypeLabel` 负责把官方字段组合解析成节点类型名称。
- 航海日志数据库继续保存解析后的节点类型文本，不修改数据库结构。
- 旧版日志中以数字保存的 `node_type` 缺少完整的 `api_event_id`，无法可靠还原节点类型，统一显示为「旧版记录」。
- 空值、空字符串和无法识别的值也显示为「旧版记录」。
- 状态筛选中不再出现「进击」；有旧版数字记录时出现「旧版记录」。

## 数据依据

当前战斗控制器已经监听以下地图 API：

- `/kcsapi/api_req_map/start`：开始出击并返回第一个节点信息。
- `/kcsapi/api_req_map/next`：玩家选择进击后返回下一个节点信息。

两个响应都由现有解析逻辑读取 `api_event_id` 和 `api_event_kind`，并写入 `BattleContext`。战斗结果通过 `battleresult` 入库时，数据库保存 `BattleContext.nodeTypeLabel`。因此，新日志已经具备基于官方字段的节点类型文本，不需要新增对 `/next` 的回写流程。

「进击」是玩家操作；「普通战斗」「Boss 战」等是节点类型。两者语义不同，本次只修正节点类型显示。

## 兼容策略

旧版本数据库曾只保存 `eventKind` 数字。单独的 `eventKind` 在不同 `eventId` 下可能代表不同节点类型，因此不能用当前映射准确恢复。

兼容规则如下：

| 原始 `node_type` | 显示结果 |
|---|---|
| 非空文本 | 原文本，例如「空袭战」 |
| 数字或数字字符串 | 「旧版记录」 |
| 空字符串或 `null` | 「旧版记录」 |
| 其他无法识别值 | 「旧版记录」 |

不执行数据库迁移，不删除旧记录，也不猜测旧数字的具体含义。

## 实现边界

- 只修改航海日志的状态格式化与筛选显示。
- 不修改 `BattleContext.nodeTypeLabel` 的官方字段映射。
- 不修改战斗记录写入时机和数据库表结构。
- 不新增玩家「进击／撤退」行为日志。
- 不改动海域、节点、评价、掉落等其他筛选与列。

## 测试

- 格式化测试：节点类型文本保持原样。
- 格式化测试：数字 `1`、`6`、未知数字和 `null` 均显示「旧版记录」。
- Widget 测试：包含旧数字记录时，状态筛选提供「旧版记录」，不提供「进击」。
- Widget 测试：新记录仍按 `BattleContext.nodeTypeLabel` 提供「资源获得」「路线选择」等筛选项。
- 回归测试：出击日志表格、筛选面板和数据库写入测试继续通过。
