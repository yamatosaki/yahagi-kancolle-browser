# 1.0.3 任务即时完成与截图修复设计

## 目标

1. 已同步且可可靠追踪的任务，在游戏操作满足目标后立即显示为已完成，不要求再次进入任务页面。
2. 复杂或缺少可靠本地判定条件的任务不得被乐观误判；任务页面返回的服务器状态始终可以校准本地结果。
3. Android 截图能够捕获硬件加速的舰C游戏 WebView，并保存到系统相册。
4. 保留旧 Android 版本的截图兼容路径，并向 Flutter 返回可诊断的失败原因。

## 非目标

- 不通过脚本主动请求或刷新游戏任务接口。
- 不把尚未建模的复杂编成、地图、击沉条件任务猜测为完成。
- 不截取应用右侧信息面板；截图范围仍为游戏 WebView。
- 不在本轮重新打包 APK。

## 任务状态设计

`GameQuest` 保留服务器的任务状态，同时增加一个从可靠本地计数推导的完成语义。满足以下任一条件时，界面显示任务已完成：

- 服务器返回 `api_state == 3`；
- 任务存在已知且可靠的本地目标，且本地当前计数达到目标计数。

本地事件处理继续在每次被捕获的游戏 API 响应后运行。计数达到目标时，首页和任务详情页会在同一次状态通知中重建，因此无需进入任务页刷新。任务仍保留在“进行中任务”集合及已接受数量中，直到玩家领取奖励或服务器任务列表删除它。

服务器任务列表再次同步时，使用服务器进度档位和状态校准本地记录。如果任务不在可靠目标目录中，仍只展示服务器状态，避免误报。

首轮覆盖现有已建模且可从单一 API 事件可靠计数的任务，包括出击/胜利、演习、远征、修理、补给、开发和建造。后续扩充 poi 目标目录时沿用同一接口，不改变 UI 语义。

## 截图设计

Android 8.0（API 26）及以上优先使用 `PixelCopy.request(window, rect, bitmap, ...)`：

1. 从当前 Activity 视图树收集可见、已附着且尺寸有效的 WebView。
2. 如存在多个候选，选择可见面积最大的 WebView，避免隐藏或过渡中的旧 WebView导致“数量不是 1”错误。
3. 将 WebView 的窗口坐标和尺寸转换成 `PixelCopy` 的源矩形。
4. 异步复制完成后检查结果码和图片内容，再保存至 MediaStore。
5. MethodChannel 结果、Bitmap 回收和异常处理都在异步回调结束后完成，确保不会提前释放资源或重复回调。

Android 7.x 及以下继续使用 `WebView.draw(Canvas)`。存储策略保持不变：Android 10 以上使用 MediaStore，旧系统在获得写入权限后写入公共 Pictures/Yahagi。

若 PixelCopy 不成功，返回包含结果码的 `pixel_copy_failed`；找不到可见游戏 WebView、尺寸无效、图片空白或相册写入失败分别保留独立错误码。Flutter 继续防止连续点击触发并发截图，并将原生错误详情显示给用户。

## 测试策略

- Dart 模型测试：可靠任务从目标前一步增加到目标值后立即呈现完成语义，且领取前仍保留在任务集合中。
- Widget 测试：首页任务胶囊与详情状态在事件到达后立即显示完成，无需 questlist 二次同步。
- Kotlin 单元测试：可见 WebView 候选选择和 PixelCopy 源矩形计算独立为纯逻辑，覆盖隐藏、零尺寸和多候选情况。
- Android 编译验证：运行 `:app:testDebugUnitTest` 和 Debug Manifest/编译任务，确认异步截图代码可编译。
- 设备验证：完整重新运行 Debug 后，在虚拟机中验证游戏截图进入相册；本轮涉及原生 Kotlin，黄色热重载和 Flutter Hot Restart 均不足以加载该部分。

## 风险与边界

- `PixelCopy` 只能复制当前屏幕中实际可见的 WebView 区域；被完全遮挡或未附着的页面会返回明确错误。
- 本地任务完成属于辅助显示结果，不替代游戏服务器判定；奖励领取和任务移除仍以游戏接口为准。
- 现有未建模任务不会获得即时完成标记，但也不会被错误标记。
