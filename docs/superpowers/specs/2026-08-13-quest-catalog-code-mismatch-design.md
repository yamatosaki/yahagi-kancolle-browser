# 任务资料跨数据源编号差异修复设计

## 背景

任务资料在线更新会合并两个上游数据源：

- `kcanotify-gamedata` 提供日文任务编号、名称、说明和奖励。
- `kcQuests` 提供任务前置关系。

两份资料都以游戏任务 ID 作为 JSON 键，但部分任务的 `code` 命名不同。当前合并器要求同一游戏任务 ID 的 `code` 完全一致，因此已知的命名差异会抛出 `FormatException`，导致关系资料发生任何更新时，整包任务资料都无法更新。

## 目标

- 以游戏任务 ID 作为跨数据源关联主键。
- 保留日文资料中的 `code`、`name`、`desc` 和显示字段。
- 仅从关系资料读取 `pre`。
- 不因关系资料中的 `code` 命名差异拒绝整包更新。
- 保留现有的结构、大小、哈希、任务数量和字段类型校验。

## 非目标

- 不修改上游数据源。
- 不维护任务 `code` 别名表。
- 不改变本地缓存、下载回退或版本比较逻辑。
- 不放宽非法任务 ID、非法 JSON 或非法前置关系的校验。

## 设计

### 合并规则

`mergeQuestCatalogJson` 继续遍历日文资料中的游戏任务 ID，并按以下职责合并字段：

| 字段 | 权威来源 |
| --- | --- |
| `code` | `kcanotify-gamedata` |
| `name` | `kcanotify-gamedata` |
| `desc` | `kcanotify-gamedata` |
| `rewards` | `kcanotify-gamedata` |
| `resources` | `kcanotify-gamedata` |
| `pre` | `kcQuests` |

关系资料中的 `code` 不参与合并，也不作为跨数据源一致性校验条件。游戏任务 ID 是双方共同使用的稳定关联键。

### 校验边界

以下校验保持不变：

- 两份资料根节点必须是 JSON 对象。
- 日文资料的游戏任务 ID 必须是正整数。
- 日文资料条目必须包含有效的 `code`、`name` 和字符串类型的 `desc`。
- 关系资料中的 `pre` 必须为空，或为非空字符串组成的数组。
- 合并结果必须通过 SHA-256、最大字节数、最少任务数量、唯一任务编号和禁止自依赖等现有校验。

如果关系资料没有对应的游戏任务 ID，合并结果不写入 `pre`，与现有行为一致。

## 数据流

1. 更新服务获取两个上游的最新不可变提交号。
2. 下载与提交号绑定的两份 JSON。
3. 合并器按游戏任务 ID 关联条目。
4. 显示字段取自日文资料，前置关系取自关系资料。
5. 合并结果经过完整数据集校验。
6. 校验通过后原子保存；失败时保留当前版本。

## 测试策略

采用测试驱动开发：

1. 在合并器测试中新增回归用例：相同游戏任务 ID、不同 `code` 时仍成功合并；结果保留日文 `code` 并导入关系 `pre`。
2. 先运行该测试，确认当前实现因 `Quest code mismatch` 失败。
3. 删除致命的跨源 `code` 相等校验，运行测试确认通过。
4. 在更新服务测试中覆盖不同 `code` 的真实更新流程，确认资料能够保存。
5. 运行任务资料相关测试与 `flutter analyze`，检查回归和静态错误。

## 成功标准

- 当前上游存在 `code` 命名差异时，任务资料更新不再显示“未通过验证”。
- 合并结果使用日文资料的 `code`，并保留关系资料提供的 `pre`。
- 所有任务资料测试通过。
- 静态分析不新增错误或警告。
